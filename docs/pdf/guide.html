1. Do I still need Docker for local development? contents ↑

Yes — but only for the three databases, never for your own code. This is the single most useful thing to understand about running this project.

FinTrack needs PostgreSQL, MongoDB and Redis. You have two honest options: install all three natively on your Mac and manage three services, or run one command and let Docker provide them. The project assumes the second. Your API and worker still run as ordinary Node processes with npm run dev — you edit a file, it restarts, you set breakpoints, exactly as normal.

So what does Docker actually give you here?

Without DockerWith Docker
Install Postgres 16, MongoDB 8 and Redis 7 by hand; keep three brew services runningOne command, correct versions, isolated from anything else on your Mac
Version drift between your machine and anyone else'sEveryone gets the same versions, pinned in docker-compose.yml
Cleaning up means uninstalling servicesdocker compose down -v and it is gone
Nowhere to demonstrate Nginx or multiple API instances--profile app --scale api=3 and it is real

The short version. docker compose up -d once per session to get your databases. Then npm run dev:api and npm run dev:worker like any other Node project. You only containerise your own code when you want to demo the full scaled stack behind Nginx — see section 4.

Both processes are required. The API alone will accept writes and return 201, but analytics, activity history and reports stay empty, because a worker is what updates them. If your portfolio looks empty, this is almost always why.

2. What the system is, in one picture contents ↑

PieceWhy it is here
PostgreSQLMoney needs ACID transactions, foreign keys and CHECK constraints. It is the only thing allowed to be authoritative.
RedisCaches expensive analytics and backs the job queue. If it dies, the system gets slower, not wrong.
MongoDBActivity events genuinely differ in shape — a trade has symbol/quantity/price, a login does not. A relational table would be mostly NULL.
BullMQRetries, exponential backoff and a visible failed set, none of which you want to hand-roll.
NginxMakes “the API is stateless” a testable claim rather than an assertion.

Colima is the container runtime this project was built against — it is open source, has no GUI and no licensing questions. Start the VM once:

One-time fix most people hit. Homebrew installs docker-compose as a standalone binary, so docker compose (with a space) may report unknown command. Link it as a CLI plugin:

mkdir -p ~/.docker/cli-plugins
ln -sfn $(brew --prefix)/opt/docker-compose/bin/docker-compose ~/.docker/cli-plugins/docker-compose

4. The two ways to run it contents ↑

Never run both at once, and stop Mode B before running tests. They share one Postgres and one Redis, so a containerised worker will silently consume the jobs your local worker or your test suite is waiting on. This cost me real debugging time — five queue tests failed with no apparent cause.

5.1 Authentication

Decode the token and look at what it actually carries:

python3 -c "import base64,json,sys;p=sys.argv[1].split('.')[1];p+='='*(-len(p)%4);print(json.dumps(json.loads(base64.urlsafe_b64decode(p)),indent=2))" "$TOKEN"
{
  "iat": 1789804364,
  "exp": 1789807964,
  "iss": "fintrack",
  "sub": "2ced0658-cedf-4fa2-aa9a-e31a241b4658"
}

Identity and nothing else. No email, no name, no role — a JWT is signed, not encrypted, so anything inside it is readable by whoever holds it.

It cannot be used to discover which emails are registered:

curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"demo@fintrack.dev","password":"wrong"}'
curl -s -X POST $API/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"nobody@fintrack.dev","password":"wrong"}'
{"error":{"message":"Invalid email or password","requestId":"2a3b16c3-…"}}
{"error":{"message":"Invalid email or password","requestId":"f8434cfb-…"}}

Identical status and message. The server also runs a dummy bcrypt comparison when no user exists, so both paths take comparable time — an identical message that returns measurably faster for unknown emails would leak the same fact through timing.

5.2 Money movement

post() { curl -s -X POST $API/transactions -H "Authorization: Bearer $TOKEN" \
         -H 'Content-Type: application/json' -d "$1"; }

post '{"type":"DEPOSIT","accountId":"'$ACC'","amount":"100000"}'
post '{"type":"BUY","accountId":"'$ACC'","symbol":"INFY","quantity":"10","price":"100"}'
post '{"type":"BUY","accountId":"'$ACC'","symbol":"INFY","quantity":"10","price":"200"}'
post '{"type":"SELL","accountId":"'$ACC'","symbol":"INFY","quantity":"5","price":"250"}'

Trade amounts come back as 1000.0000 and 2000.0000 — computed server-side as quantity × price. Sending your own amount on a trade is rejected, or a client could set its own price.

Money is always a string, never a JSON number:

curl -s $API/accounts -H "Authorization: Bearer $TOKEN" | jq '.accounts[0].balance'
"98250.0000"     ← quoted

JSON numbers are IEEE-754 doubles. A client parsing 12345678.91 can silently receive something else, so every monetary value crosses the wire as a decimal string.

Overdraft refused:

post '{"type":"WITHDRAWAL","accountId":"'$ACC'","amount":"9999999"}' | jq
{
  "error": {
    "message": "Insufficient funds",
    "details": ["available 98250.0000, required 9999999.0000"],
    "requestId": "54fb62de-…"
  }
}

Short selling refused:

"Insufficient holdings"
"TCS: holding 0.00000000, attempted to sell 1.00000000"

A deposit carrying trade fields is refused, not silently ignored — an unexpected field on a money movement means the client believes it is doing something the server is not.

5.3 Analytics

Wait two seconds after writing; a worker updates these, not the request.

curl -s $API/analytics/portfolio -H "Authorization: Bearer $TOKEN" | jq
{
  "cash": { "total": "98750.0000", "accounts": 1 },
  "holdings": [{
    "symbol": "INFY",
    "quantity": "15.00000000",
    "averageBuyPrice": "150.0000",
    "costBasis": "2250.0000",
    "realizedPnl": "500.0000"
  }],
  "totals": { "symbols": 1, "costBasis": "2250.0000",
              "marketValue": null, "unrealizedPnl": null }
}

Check the arithmetic yourself — this is the number to be able to defend.

Bought 10 @ 100 and 10 @ 200 → 20 units costing 3,000 → average 150.
Sold 5 @ 250 → realised (250 − 150) × 5 = 500.
Left with 15 units at a basis of 3,000 − (5 × 150) = 2,250.

marketValue and unrealizedPnl are null on purpose. There is no price feed, and a number derived from cost basis would look like a valuation without being one. The P&L endpoint states "method": "WEIGHTED_AVERAGE" so a consumer never has to guess which cost-basis rule produced the figure.

5.4 Activity history — and why MongoDB is here

curl -s "$API/activity?limit=10" -H "Authorization: Bearer $TOKEN" \
  | jq -r '.events[] | "\(.eventType)  \(.entityType)"'
TRADE_EXECUTED       transaction
TRADE_EXECUTED       transaction
DEPOSIT_COMPLETED    transaction
LOGIN                user
USER_REGISTERED      user

Now look at the metadata of each. A trade carries symbol, quantity, price. A registration carries an email. A plan carries a frequency. One relational table holding all of those would be mostly NULL columns — that is the concrete answer to “why not just use Postgres JSONB?”: this collection needs no joins and no transactions, so it gains nothing from being relational.

5.5 Reports — the async boundary made visible

TODAY=$(date +%F)

  | grep -iE '^HTTP|retry-after'

202, not 404. The report does not exist yet — and asking for it queued its generation. Ask again a few seconds later:

6. The six guarantees, and how to prove each contents ↑

These are the properties worth demonstrating in an interview. Each one is observable, not asserted.

#GuaranteeHow you see it
6.1A retried POST creates one transaction201 then 200; five concurrent retries return identical ids
6.2Concurrent withdrawals cannot both passtwo × 60 against 100 → one 201, one 422, balance 40.0000
6.3Redis failing costs latency, not correctnessstop Redis → still 200, same figures, x-cache: MISS
6.4An event is never lost between commit and queuestop worker → row waits in the outbox → restart → drains to 0
6.5The same event twice changes nothing twiceprocessed_events ledger / Mongo unique index
6.6Aggregates are order-independentthree trades fired concurrently still give 2250 / 500

6.1 Idempotency

KEY="demo-$(date +%s)"
curl -s -o /dev/null -w 'first:  %{http_code}\n' -X POST $API/transactions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $KEY" -d '{"type":"DEPOSIT","accountId":"'$ACC'","amount":"500"}'
curl -s -o /dev/null -w 'second: %{http_code}\n' -X POST $API/transactions \
  -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $KEY" -d '{"type":"DEPOSIT","accountId":"'$ACC'","amount":"500"}'
first:  201
second: 200

200, not 201. A 201 would claim a second transaction was created — exactly what idempotency prevented. The body is the original transaction with "replayed": true.

Now under real concurrency — five simultaneous retries of one key:

KEY="race-$(date +%s)"
for i in 1 2 3 4 5; do
  curl -s -X POST $API/transactions -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' -H "Idempotency-Key: $KEY" \
    -d '{"type":"DEPOSIT","accountId":"'$ACC'","amount":"250"}' | jq -r .transaction.id &
done; wait

Five identical ids. One transaction, one balance movement. Two mechanisms are at work: a lookup inside the row lock catches sequential retries, and a unique index catches the concurrent ones — one request loses that race and is resolved to the winner's row.

6.2 Lost updates

for i in 1 2; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST $API/transactions \
    -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
    -d '{"type":"WITHDRAWAL","accountId":"'$ACC2'","amount":"60"}' &
done; wait
201
422
final balance: 40.0000

Without SELECT … FOR UPDATE both requests read a balance of 100, both conclude 60 is affordable, and the account lands at −20. The lock serialises them; the CHECK (balance >= 0) constraint is the database-level backstop if the service is ever wrong.

6.3 Cache failure

docker compose stop redis
curl -s -o /dev/null -w 'status: %{http_code}\n' $API/analytics/portfolio -H "Authorization: Bearer $TOKEN"
curl -s $API/health | jq '.status, .checks.redis.status'
docker compose start redis
status: 200
"ok"
"down"

Still 200, same correct figures, and /health reports healthy overall with Redis marked down. Postgres down is the opposite — 503 — because nothing can be served correctly without the source of truth.

6.4 The outbox

Stop the worker, write a transaction, and watch the event wait durably:

docker compose exec -T postgres psql -U fintrack -d fintrack -c \
  "SELECT event_type, published_at FROM outbox_events WHERE published_at IS NULL;"

The row sits there with published_at NULL. Start the worker and it drains to zero. The event and the balance change were written in one transaction, so there is no window in which the money moved but the event vanished.

6.6 Order independence — a bug this document found

This was a real defect, discovered while writing this guide. Weighted-average cost basis is order-dependent, and the worker processes jobs concurrently. Three trades on one account were claimed within milliseconds and then raced for the holding row lock — which serialises the writes but does not order them.

The result: a cost basis of 2,500 and realised P&L of 750, instead of 2,250 and 500. Exactly what you get by applying the sale before the second purchase. Nothing errored; the numbers were simply plausible and wrong.

Fix (ADR-019): a trade event no longer mutates the holding. It recomputes it by replaying that symbol's trades from the transaction log, so the result is identical whatever order events arrive in — and a late event now heals the aggregate instead of corrupting it.

for t in BUY_100 BUY_200 SELL_250; do ... done      # fire all three back to back
sleep 4
curl -s $API/analytics/portfolio -H "Authorization: Bearer $TOKEN" \
  | jq '.holdings[] | select(.symbol=="WIPRO")'
{
  "quantity": "15.00000000",
  "averageBuyPrice": "150.0000",
  "costBasis": "2250.0000",
  "realizedPnl": "500.0000"
}

Must be these four values every time. If you ever see 2500 and 750, the sale was applied before the second purchase.

7. Looking inside the three databases contents ↑

PostgreSQL

docker compose exec -it postgres psql -U fintrack -d fintrack
\dt                 -- tables
\di                 -- indexes
\d transactions     -- one table in full, constraints included

The business rules the database enforces itself — not the application:

SELECT conrelid::regclass AS "table", conname
FROM pg_constraint WHERE contype='c' AND connamespace='public'::regnamespace ORDER BY 1;
accounts          | chk_accounts_balance_non_negative
investment_plans  | chk_plans_amount_positive
subscriptions     | chk_subscriptions_ended_at
transactions      | chk_transactions_amount_positive
transactions      | chk_transactions_price_positive
transactions      | chk_transactions_quantity_positive
transactions      | chk_transactions_trade_fields

Try to break one by hand. It should refuse — this is the demonstration that correctness does not depend on the application being right:

UPDATE accounts SET balance = -1 WHERE id = (SELECT id FROM accounts LIMIT 1);
ERROR:  new row violates check constraint "chk_accounts_balance_non_negative"
INSERT INTO transactions (id, account_id, type, amount)
VALUES (gen_random_uuid(), (SELECT id FROM accounts LIMIT 1), 'BUY', 100);
ERROR:  new row violates check constraint "chk_transactions_trade_fields"
        -- a BUY with no symbol

Operational queries you will actually use:

-- is anything stuck in the outbox?
SELECT event_type, count(*), count(*) FILTER (WHERE published_at IS NULL) AS unpublished
FROM outbox_events GROUP BY 1;

-- rows that keep failing to publish
SELECT id, event_type, attempts, last_error FROM outbox_events
WHERE published_at IS NULL AND attempts > 0;

-- the pre-aggregated state the analytics endpoints read
SELECT * FROM portfolio_holdings;
SELECT * FROM daily_user_aggregates ORDER BY day DESC LIMIT 5;

MongoDB

docker compose exec -it mongodb mongosh fintrack
db.activity_events.countDocuments({})
db.activity_events.find().sort({occurredAt:-1}).limit(5).pretty()
db.activity_events.getIndexes()
db.report_snapshots.find().pretty()
indexes: _id_, user_time, user_type_time, event_id_unique

event_id_unique is the idempotency guard for the activity writer. It cannot use the Postgres processed_events ledger, because its write and that ledger live in different databases and cannot share a transaction — claiming first and then failing to write would lose the event while the ledger insisted it was handled.

Redis

docker compose exec -it redis redis-cli
KEYS analytics:*                 # cached analytics, one set per user
TTL analytics:user:<id>:portfolio
KEYS bull:*                      # BullMQ queue state
LLEN bull:analytics:wait         # queue depth — growing means workers cannot keep up

8. Tests, benchmarks and load results contents ↑

The test suite

docker compose up -d
docker compose --profile app stop api worker nginx   # if the full stack is running
npm test
Test Suites: 11 passed, 11 total
Tests:       153 passed, 153 total
Time:        ~50 s

These run against real PostgreSQL, MongoDB and Redis. Mocks cannot demonstrate row locking, transaction rollback or cache fallback — the behaviour only exists against the real thing. They run serially because several suites truncate a shared database.

A few of the things they assert:

TestWhy it matters
A forced failure mid-transaction rolls back the balance and the outbox rowProven with a real NUMERIC overflow, not a mock
Two concurrent withdrawals: exactly one succeedsThe lost-update race, run for real
Five simultaneous retries of one key → one transactionIdempotency under contention, not just sequentially
Analytics correct with Redis genuinely stoppedThe container is stopped, not a client mocked to throw
Three trades applied in reverse order → correct stateRegression guard for the ADR-019 bug

Index benchmark

npm run seed -- --users=200 --transactions=500000        # ~30 s
docker compose exec -T postgres psql -U fintrack -d fintrack -f db/benchmark/explain.sql

The interesting part is that the slow plan is not a sequential scan. Postgres falls back to the idempotency index, which also starts with account_id, finds the 2,665 matching rows, then has to read every one from the heap and sort them to return 20. The cost is in reading the rows, not in finding them.

Load tests

docker compose --profile app up -d --scale api=3 --scale worker=2
k6 run load/smoke.js          # is the stack wired up?
k6 run load/read-heavy.js     # cached analytics
k6 run load/write-heavy.js    # deposits under lock contention
ScenarioThroughputp50p95Failed
Read-heavy (cached analytics, 20 VUs)5,107 req/s2.72 ms6.46 ms0.000%
Write-heavy (deposits, one account, 10 VUs)361 req/s9.09 ms94.22 ms0.000%

The write run produced 16,437 outbox rows, which two workers drained to a backlog of zero.

What these numbers are not. The load generator shares four CPU cores with the entire stack, so they are a floor rather than a ceiling. The read test runs at a 100% cache hit rate against a single user — it measures the cached path, which is the point of the cache and also the limit of the number. 500k rows fit comfortably in page cache at this VM size; behaviour at 50M rows is untested. None of it is a capacity claim.

Recording those caveats beside the figures is the difference between a measurement and a marketing number.

9. Scaling it and proving it scaled contents ↑

docker compose --profile app up -d --scale api=3 --scale worker=2

Prove requests actually distribute

for i in $(seq 1 30); do
  curl -s -D - -o /dev/null http://localhost:8080/health | grep -i '^x-instance-id'
done | sort | uniq -c
  10 x-instance-id: api-bfa969b0a202
  10 x-instance-id: api-d8b2ad8002a8
  10 x-instance-id: api-ebcbc4688633

Each container reports its own hostname. An even split across three instances.

Prove the API is stateless

A token issued by one instance is accepted by all of them — nothing session-related is held in process memory, which is what lets any instance serve any request:

HTTP/1.1 200 OK  x-instance-id: api-bfa969b0a202
HTTP/1.1 200 OK  x-instance-id: api-d8b2ad8002a8
HTTP/1.1 200 OK  x-instance-id: api-ebcbc4688633
…

Prove two workers do not double-process

docker compose exec -T postgres psql -U fintrack -d fintrack -c \
  "SELECT count(*) AS outbox FROM outbox_events;
   SELECT processor, count(*) FROM processed_events GROUP BY 1;"

Each event appears once per processor, never twice. The publisher claims rows with FOR UPDATE SKIP LOCKED, so two publishers take disjoint sets rather than both grabbing the head of the backlog.

Scale the workers alone when the queue backs up but request latency is fine — that independence is the concrete reason the API and worker are separate processes:

docker compose --profile app up -d --scale worker=4

11. The 90-second demo contents ↑

If you have to show this quickly — in an interview, or to a reviewer.

docker compose --profile app up -d --scale api=3 --scale worker=2
API=http://localhost:8080
TOKEN=$(curl -s -X POST $API/auth/register -H 'Content-Type: application/json' \
  -d '{"email":"demo-'$(date +%s)'@x.dev","name":"Demo","password":"correct-horse-battery"}' | jq -r .token)
ACC=$(curl -s -X POST $API/accounts -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"accountType":"BROKERAGE"}' | jq -r .account.id)
#ShowSay
1curl -s $API/health | jqThree subsystems, probed independently. Postgres down is a 503; Redis down is not.
2Deposit, buy twice, sell onceEach is one database transaction: row lock, insert, balance, outbox — all or nothing.
3/analytics/portfolioUpdated by a worker, not by the request. The API never waited for it.
4Run it twice, show x-cacheMISS then HIT. Cache-aside, 10-minute TTL, invalidated by the worker on write.
5docker compose stop redis, run againStill 200, still correct. The cache is an optimisation; Postgres is the truth.
6/activitySame events from MongoDB, with per-type metadata a relational table would store as NULLs.
7The 30-request instance-id loopThree instances sharing load; a token from one works on all — nothing in process memory.

Then say the thing that actually matters:

“The API never waits for the worker, and the worker can be restarted, duplicated or crashed without losing an event or double-counting one.”
